PostgreSQL Indizes richtig einsetzen — ein Leitfaden mit EXPLAIN ANALYZE

#postgres #performance #datenbanken
M @mara vor 3 Std. bearbeitet (vor 2 Std.)
+87

Ein Index ist kein Selbstzweck. Er beschleunigt das Lesen und verlangsamt jedes Schreiben. Die Frage ist deshalb nie „brauchen wir einen Index?", sondern „welche Abfrage soll schneller werden, und was kostet uns das?".

Erst messen, dann indizieren

Bevor irgendein CREATE INDEX entsteht, lohnt ein Blick auf den tatsächlichen Plan. PostgreSQL verrät in EXPLAIN (ANALYZE, BUFFERS) nicht nur Schätzungen, sondern auch, wie viele Zeilen wirklich gelesen wurden.

EXPLAIN (ANALYZE, BUFFERS)
SELECT id, title FROM threads
WHERE category_id = 4
ORDER BY created_at DESC
LIMIT 20;

Steht dort ein Seq Scan über 400.000 Zeilen, ist das ein Kandidat für einen Index. Steht dort ein Index Scan, der ohnehin schnell ist, dann ist der neue Index nur Schreiblast.

Composite statt vieler Einzelindizes

Für Filter plus Sortierung ist ein zusammengesetzter Index fast immer die bessere Wahl:

  • (category_id, created_at DESC) bedient Filter und Sortierung in einem Zug.
  • Die Reihenfolge der Spalten folgt der Kardinalität — die selektivere Spalte zuerst.
  • Ein zusätzlicher Teilindex auf WHERE deleted_at IS NULL hält den Index klein.
Faustregel: Jeder Index, der nie in einem Plan auftaucht, ist reine Schreiblast. Wir prüfen unsere Indizes deshalb quartalsweise mit pg_stat_user_indexes.

Wie geht ihr vor? Nutzt ihr pg_stat_statements oder verlasst ihr euch auf das langsame Query-Log?
